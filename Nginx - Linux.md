# Nginx

Nginx -это серверное приложение (веб-сервер), который занимается пересылкой запросов на бэкенд; отдачей статических данных (картинки, html-страницы); балансировкой трафика между бэкендами; расшифровкой `https` (TLS/SSL); кэшированием данных от бэкенда, для разгрузки бэкенда; ограничением трафика, для защиты от DDoS-атак; сжатием данных от бэкенда, для ускорения отправки до клиента; обработкой ошибок от бэкенда и переделывание их в формат, удобный для восприятия пользователем.  

Nginx сервер, как правило, стоит "перед дверью" в инфраструктуру  ресурса. Он принимает запросы от клиента и управляет трафиком бэкенда, в конечном итоге nginx возвращает ответ от бэкенда клиенту.

Основные настройки данного веб-сервера хранятся по пути `/etc/nginx/nginx.conf`. Настройка самих сайтов описывается в конфигурационных файлах по пути `/etc/nginx/sites-available/`. Эти файлы состоят из настроек по какому порту будет
прослушиваться сайт, какое имя сервера (`server_name`) должно быть, где сайт должен искать ресурсы, и так далее.  
Файл `/etc/nginx/nginx.conf` смотрит в путь `/etc/nginx/sites-enabled/` и включает файлы по этому пути в себя. В директории `/etc/nginx/sites-enabled/` находятся символьные ссылки (ярлыки) на файлы директории `/etc/nginx/sites-available/`, Это гениальное решение `Ubuntu`, которое позволяет быстро отключать сайты, просто удалив ярлык в `/etc/nginx/sites-enabled/`.
## Конфигурации сайтов по пути `/etc/nginx/sites-available/`
### Конфигурация обычного http сайта
```nginx
server {
    listen <порт>;
    server_name <имя сервера>;
    # Статическая отдача ресурсов
    location / { # Если запрос начинается с /
        root <каталог, где располагаются ресурсы>; # ищет в <каталог, где располагаются ресурсы>
        index <html файл>; # Если просто запрашивают /, возвращают <html файл>
        # Проверка файлов
        try_files $uri $uri/ =404; # Расписано ниже, после склейки.
    }
}
```
#### Склейка
Склейка - это процесс преобразования uri из запроса в путь до файла на самом сервере.  
Принцип склейки простой: `путь на сервере` = `root` + `uri из запроса`  
Например: пользователь в строчку браузера вводит `http://test_site.org/second_page.html`.  
`root` прописан следующим образом `root /data/test_site/www/`. В итоге финальный запрос будет направлен на путь `/data/test_site/www/second_page.html`.  
Данный пример работает только при одной секции `location`.  

Если в файле конфигурации сайта существуют несколько секций `location`, тут работает правило "самое длинное совпадение".  
Это правило говорит, если `<путь>` в `location <путь>` самый длинный, то этот `location <путь>` первый в очереди на проверку.  
Рассмотрим пример. У нас есть следующий конфигурационный файл
```nginx
server {
    listen 80;
    server_name _;

    location / { 
        root /data/test_site/www;
        try_files $uri $uri/ =404;
    }

    location /images/ { 
        root /data/test_site/resurses;
        try_files $uri $uri/ =404;
    }
}
```
Когда пользователь пишет в строку браузера `http://test_site.org/images/logo.png` ngnix берет `/images/` и проверяет по секциям`location`. В первую очередь он будет идти по самым длинным секциям`location`. В нашем примере существует одна такая секция `/images/`, ngnix берет, сравнивает, идет совпадение и происходит привычный нам процесс склейки `путь на сервере` = `root` + `uri из запроса`. `/data/test_site/resurses` + `/images/logo.png` = `/data/test_site/resurses/images/logo.png`

#### Команда `try_files $uri $uri/ =404`
Данная команда - это инструкция для nginx, которая объясняет, как искать файл и что делать, если файла нет.  
Команда `try_files $uri $uri/ =404` выполняется строго слева направо. Когда находится первое совпадение, процесс проверки останавливается.   

Первая проверка `$uri` - это путь запроса пользователя. Например `http://test_page.org/first_page.html`, тут `uri` будет `/first_page.html`. Nginx берет склейку и проверяет, если ли такой файл на диске.
Вторая проверка `$uri/`. На этой проверке выясняется, есть ли вообще директория `/`.
Возврат ошибки `=404`. Если проверка не удовлетворилась, возвращается ошибка 404.

### Конфигурация https сайта
Для конфигурации сайта, который бы работал по протоколу https нужны сертификаты.
Файл конфигурации выглядит следующим образом:
```nginx
server {
    listen 80;
    server_name _;
    return 301 https://$host$request_uri;  # 301 - перемещен навсегда на https:<сайт, набранный пользователем><запрос пользователя>
}

server {
    listen 443 ssl; ## прослушка 443 порта с расшифрованием ssl
    server_name _;

    # пути к самоподписанному сертификату и ключу
    ssl_certificate /etc/ssl/certs/<сертификат>; # публичный сертификат
    ssl_certificate_key /etc/ssl/private/<ключ>; # приватный ключ

    location / {
        root <каталог, где располагаются ресурсы>; # ищет в <каталог, где располагаются ресурсы>
        try_files $uri $uri/ =404;
    }
}
```
### Конфигурация Reverse Proxy

Reverse Proxy - это механизм "тайной" пересылки трафика на бэкенд.

Золотой стандарт настройки файла конфигурации для Reverse Proxy

```nginx
server {      
    listen <listening port>;      
    server_name _;      
      
    location / {      
    # Перенаправляем все запросы на адрес и порт бэкенда
        proxy_pass http://<ip сервера>:<порт сервиса>;
        # Передаем правильные заголовки, чтобы бэкенд знал, кто его просит      
        proxy_set_header Host $host; # Берет имя сайта, которое набрал пользователь, и передает его бэкенду.
        proxy_set_header X-Real-IP $remote_addr; # Передает IP клиента бэкенду (для отслеживания трафика, чтобы можно было заблокировать злоумышленника).
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; #  Создает цепочку IP-адресов, если запрос идет через несколько прокси. Цепочка следующая: <ip клиента> - <ip прокси сервера(ов)>
    }      
}
```
### Конфигурация https Reverse Proxy
```nginx
server {
    listen 80;
    server_name _;
    return 301 https://$host$request_uri;  # 301 - перемещен навсегда на https:<сайт, набранный пользователем><запрос пользователя>

    ssl_certificate /etc/ssl/certs/<сертификат>; # публичный сертификат
    ssl_certificate_key /etc/ssl/private/<ключ>; # приватный ключ

    location / {
           # Перенаправляем все запросы на адрес и порт бэкенда
        proxy_pass http://<ip сервера>:<порт сервиса>;
        # Передаем правильные заголовки, чтобы бэкенд знал, кто его просит      
        proxy_set_header Host $host; # Берет имя сайта, которое набрал пользователь, и передает его бэкенду.
        proxy_set_header X-Real-IP $remote_addr; # Передает IP клиента бэкенду (для отслеживания трафика, чтобы можно было заблокировать злоумышленника).
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; #  Создает цепочку IP-адресов, если запрос идет через несколько прокси. Цепочка следующая: <ip клиента> - <ip прокси сервера(ов)>
        proxy_set_header X-Forwarded-Proto $scheme; #Направляет запросы по http протоколу бэкенду, и говорит, чтобы бэкенд генерировал ссылки https
    }
}
```
